# Designo Custom Theme（マルチページ・カスタムテーマ構築実績）

実務を想定した大規模なデザインカンプ（複数画面・複雑なページレイアウト）をもとに、標準的なスターターテーマをベースに、実務要件に合わせて設計・拡張実装した独自カスタムテーマの開発実績です。
単なる外観のトレースや既存テーマのカスタマイズにとどまらず、WordPressのテンプレート階層に則ったコンポーネント設計、BEM思想に基づくSassモジュール化、実務運用を見据えたアセット最適化など、「保守性の高さ」と「運用のしやすさ」を考慮して構築しました。

## 概要

### 要件・機能

全7画面（トップ、About、App Design、Web Design、Graphic Design、Locations、Contact）にわたる複雑なグリッドレイアウトや有機的な装飾（背景のリーフパターン等）を含むデザインをドット単位で忠実にトレース。さらに、以下のテーマ機能を実装しました：

- **マルチページ（MPA）ナビゲーション & フルレスポンシブ設計:** スマホ・タブレット・PCの全環境でデザインが滑らかに追従。
- **動的アセット管理:** `functions.php` をコアとしたアセット読み込み制御とWordPress標準機能（`title-tag`, `html5`）の全般サポート。
- **実務に耐えうる拡張性:** 今後のプラグイン導入や固定ページ増設時に、既存コードに悪影響を与えにくいカプセル化。

## 開発プロセス

### ディレクトリ構造

WordPressの標準コーディング規格および npm スクリプトを活用したローカルビルド環境に則り、ソースコード側は「機能・役割ごとのモジュール（JS/SCSS）」に細かく分離。コンパイル後の成果物を `assets/` に集約し、テンプレート側から動的に読み込むクリーンでスケールしやすいディレクトリ構造を設計しています。

```text
designo-theme/
├── assets/                  # コンパイル済みアセット・静的ファイル
│   ├── css/
│   │   └── style.css        # コンパイル後のメインCSS
│   ├── js/
│   │   └── script.js        # メインJavaScript（ドロワーメニュー等の制御）
│   └── images/              # 各種画像・SVGアセット（デバイス毎に最適化）
│
├── src/                     # ソースコード開発ディレクトリ
│   └── scss/                # Sass 開発環境
│       ├── style.scss       # 各SCSSモジュールを統合するメインSCSS
│       ├── _common.scss     # 変数（カラー、流体フォント設定）、共通パーツ
│       ├── _header.scss     # ヘッダー・ナビゲーション・ドロワー
│       ├── _footer.scss     # フッター・全画面共通CVエリア
│       ├── _top.scss        # トップページ専用スタイル
│       ├── _about.scss      # 企業情報ページ専用スタイル
│       ├── _design.scss     # 実績・制作物一覧専用スタイル
│       ├── _locations.scss  # ロケーションページ専用スタイル
│       └── _contact.scss    # お問い合わせページ（Snow Monkey Form連動用）
│
├── functions.php            # テーマ設定、各種アセットのフック読み込み・最適化
├── header.php               # サイト共通ヘッダー（セマンティックなナビゲーションマークアップ）
├── footer.php               # サイト共通フッター（および全ページ共通CVエリアの統合）
├── index.php                # メインインデックス（フォールバック用）
├── page-about.php           # 固定ページテンプレート：OUR COMPANY
├── page-app-design.php       # 固定ページテンプレート：APP DESIGN（実績ページ）
├── style.css                # WordPressテーマ定義用スタイルシート
├── package-lock.json        # 依存ライブラリのバージョンロック
└── package.json             # ローカル開発用パッケージ（sass, browser-sync等）の定義
```

### 使用技術・環境
言語・マークアップ: PHP 8.x / HTML5 / SCSS (Sass Modules対応) / Vanilla JS (ES6+)

プラットフォーム: WordPress 6.x (独自カスタムテーマ)

ローカル開発環境・ツール: sass / browser-sync / concurrently (ローカル同期・高速コンパイル環境)

### こだわった技術的アプローチ
#### 1. テンプレート階層の準拠とコンポーネントのモジュール化
WordPressの標準機能であるテンプレート階層（page-{slug}.php）を適用し、各固定ページ固有のロジックを分離しました。また、header.php と footer.php にサイト共通コンポーネント（全画面共通のCVエリアを含む）を共通化することでマークアップの二重管理を防ぎ、デザインや文言の変更時に一箇所を修正すれば全画面に反映される設計を行っています。

#### 2. filemtime() を活用したキャッシュバスター環境
実務のサイト運用において、CSSやJSを変更した際にブラウザの古いキャッシュによってデザイン崩れや挙動不審が起こる課題に対応するため、functions.php 内で wp_enqueue_style / wp_enqueue_script を用いて読み込む際、PHPの filemtime() 関数を組み込みました。
ファイルの最終更新日時（タイムスタンプ）をクエリパラメータとして自動付与することで、手動でバージョンを書き換える手間を省き、最新のアセットが確実に適用される環境を整えました。

#### 3. @use 規則に準拠した Sass モジュール設計（関心の分離）
グローバルな @import によるスタイルの衝突や意図しない上書きリスクを避けるため、Sass Modules（@use）を採用しました。
カラーコードや共通設定は _common.scss に集約して一元管理し、画面やパーツ（_header.scss, _about.scss 等）ごとにファイルをカプセル化。適切な名前空間内で変数を呼び出すことで、将来的なページ増設時にもクラス名の衝突が起きにくい保守性の高いCSS設計を意識しました。

#### 4. Vanilla JS による軽量なドロワーメニュー実装
ハンバーガーメニューなどのUI制御において、外部ライブラリに依存せず Vanilla JS（ES6+）のみで軽量に構築しました。
DOMContentLoaded イベントを起点にクラスの切り替えを行い、オーバーレイ部分のクリックイベントもハンドリングすることで、スムーズで直感的なUI操作を実現しています。

#### 5. 流体フォントサイズと picture 要素によるレスポンシブ対応
デバイスの境界でレイアウトが不自然に崩れるのを防ぐため、フォントサイズや余白に vw（Viewport Width）を用いた流体設計を導入しました。
また、デバイスごとの画像切り替え（モバイル/タブレット/デスクトップ）には HTML5 の  および  要素を活用し、JavaScript による計算コストを抑え、パフォーマンスを意識した実装を行っています。

#### 6. 実務プラグイン（Snow Monkey Form）のスタイル調整
お問い合わせページ（_contact.scss）の実装では、実務で採用されることが多いブロックエディタ対応プラグイン Snow Monkey Form の出力クラス（.snow-monkey-form, .smf-item 等）にあわせたスタイルコーディングを行いました。
プラグインが生成するDOM構造やエラーメッセージの表示位置に対応させることで、運用者が管理画面から直感的にフォームを変更・運用できる体制を想定しています。

### 今後の拡張計画
**カスタムテンプレートパーツ（get_template_part）のさらなる切り出し**:
現在各固定ページ内に記述されている下部ナビゲーションエリア（projects wrap セクション）などを、template-parts/ ディレクトリへコンポーネントとして完全に切り出し、テンプレート側の記述量をさらに削減・効率化します。

**画像パス出力用のカスタムヘルパー関数の導入**:
各テンプレート内に存在する <?php echo get_template_directory_uri(); ?>/assets/images/... の記述を、独自のショートハンド関数（例: get_theme_img_url()）化し、HTMLの可読性の向上とコーディング速度の最大化を図ります。
